## 1. Введение

Данный документ представляет собой техническое задание на проектирование и разработку комплексной информационной системы для управления 3D-печатью и сопутствующими бизнес-процессами. Цель проекта заключается в создании едиYной платформы, объединяющей процессы приема заказов, подготовки моделей, управления ресурсами и финансами, а также обеспечивающей эффективное управление предприятием 3D-печати.

Документ состоит из описания функциональных требований, структуры системы, сценариев использования, архитектурных особенностей и рекомендаций по внедрению и сопровождению.

## 2. Назначение и цели проекта

Целью проекта является создание автоматизированной информационной системы, предназначенной для комплексного управления бизнесом 3D-печати. Проект охватывает все ключевые аспекты, начиная от приёма заказов и заканчивая финансовым учётом и управлением ресурсами.

Основные задачи проекта включают:
- Приём и обработку заказов на печать 3D-изделий.
- Автоматическое преобразование файлов моделей в формат STL.
- Эффективное управление размещением объектов на печатном столе.
- Учёт состояния оборудования и проведение ремонтных работ.
- Управление запасами материалов и расходниками.
- Калькуляцию себестоимости, цен и прогнозирование прибыли.
- Ведение налогового учёта и подготовку деклараций для самозанятых предпринимателей.

## 3. Требования к системе

### 3.1 Функциональные требования

#### 3.1.1 Приём и обработка заказов
- **Приём файлов моделей**: поддержка форматов STL, GLTF, OBJ, 3MF.
- **Редактор моделей**: возможность предварительного просмотра и окрашивания зон разными цветами и материалами.
- **Подготовка к печати**: определение объёма филамента, необходимого для печати, и предварительная оценка времени.
- **Выбор типа печати**: возможность выбора режимов печати (single-material, multi-material).
- **Резервирование ресурсов**: закрепление принтера и материалов за конкретным заказом.

#### 3.1.2 Управление оборудованием
- **Мониторинг состояния оборудования**: система ведёт журнал поломок, ремонтных работ и графика профилактики.
- **Управление рабочим столом**: автоматическое размещение объектов на столе с целью максимальной экономии места.
- **Планирование очередей печати**: система расставляет приоритеты между заказами и распределяет задачи между свободными принтерами.

#### 3.1.3 Управление материалами
- **Учёт наличия материалов**: ведение точной инвентаризации материалов и расходников.
- **Контроль поставок**: уведомление при низком уровне запасов и потребность в пополнении.
- **Информация о ресурсах**: мониторинг доступности материалов и сроки годности.

#### 3.1.4 Финансовый модуль
- **Регистрация доходов и расходов**: система хранит записи о поступлении денег и произведённых затратах.
- **Создание налоговой декларации**: построение налоговой документации для уплаты налогов в качестве самозанятого предпринимателя.
- **Прогнозирование прибыли и убытков**: инструмент для составления долгосрочного прогноза и оценки рентабельности бизнеса.

#### 3.1.5 Административные функции
- **Панель администрирования**: удобный интерфейс для настройки параметров системы и управления пользователями.
- **Настройки безопасности**: ограничение доступа к чувствительной информации.
- **Логирование активности**: журналы событий и аудита действий пользователей.

### 3.2 Нефункциональные требования

- **Производительность**: минимальная задержка при обработке запросов, оперативное предоставление статистических данных.
- **Безопасность**: защищенность персональных данных заказчиков и финансовых сведений.
- **Масштабируемость**: способность к горизонтальному масштабированию для увеличения числа обрабатываемых заказов.
- **Совместимость**: совместимость с современными операционными системами и устройствами.

## 4. Организационная структура системы

### 4.1 Бизнес-процессы

Бизнес-процессы системы состоят из следующих фаз:

1. **Приём заказа**: заказчик загружает файл модели, выбирает материалы и количество изделий.
2. **Подготовка к печати**: преобразование файлов, оценка требуемого количества филамента и времени печати.
3. **Печать**: управление очередью печати, контроль за ходом выполнения заказа.
4. **Завершение заказа**: передача заказчику готовой продукции, закрытие заказа.
5. **Финансовый учёт**: регистрация доходов и расходов, начисление налогов.

### 4.2 Участники процесса

- **Администрация**: руководители, операторы принтеров, менеджеры по продажам.
- **Пользователи**: клиенты, осуществляющие заказ 3D-печати.
- **Технические специалисты**: сотрудники, занимающиеся ремонтом и обслуживанием оборудования.

## 5. Структура системы

### 5.1 Блоки системы

Система делится на следующие крупные блоки:

- **Backend**: реализует основную логику обработки заказов, связь с оборудованием и управление ресурсами.
- **Frontend**: интерфейс взаимодействия пользователя с системой.
- **Рабочие сервисы**: Celery для фоновых задач, таких как преобразование файлов и расчет объемов.
- **Хранилище данных**: СУБД для хранения информации о заказах, оборудовании и материалах.

### 5.2 Внутренняя архитектура

Архитектура построена на принципах слоёв:

- **User Interface Layer**: интерфейс пользователя (Nuxt/Vue).
- **Business Logic Layer (BLL)**: логика обработки данных и правил (Django/FastAPI).
- **Data Access Layer (DAL)**: хранилище данных (PostgreSQL, Redis).
- **Infrastructure Services**: Celery, RabbitMQ, MinIO.

### 5.3 Бизнес-логика (BLL)

Основной задачей BLL является принятие запроса от Presentation слоя, обработка его согласно правилам бизнес-логики и передача запросов DAL слою для манипуляции данными.

#### 5.3.1 Сервисы и обработчики

- **Services**: представляют собой высокоуровневые классы, содержащие бизнес-логику для каждого доменного объекта. Например, существуют сервисы для работы с заказами (`OrderService`), клиентами (`CustomerService`) и материалами (`MaterialService`).

- **Handlers**: отвечают за обработку конкретных действий (создания, обновления, удаления объектов). Они выполняют дополнительную проверку данных и вызывают методы сервисов.

### 5.4 Доступ к данным (DAL)

Основная роль DAL — отвечать за доступ к источникам данных, будь то реляционная база данных, NoSQL хранилище или внешний API.

#### 5.4.1 Репозитории

- **Repositories**: классы, предназначенные для извлечения и сохранения данных. Каждое доменное понятие (заказ, изделие, принтер и т.д.) имеет соответствующий репозиторий, позволяющий абстрагироваться от конкретной реализации хранения данных.

Например, класс `OrderRepository` отвечает за работу с данными о заказах:

```python
class OrderRepository:
    def find_by_id(self, order_id):
        pass

    def save_order(self, order):
        pass

    def delete_order(self, order_id):
        pass
```

#### 5.4.2 Unit of Work

Паттерн Unit of Work применяется для управления транзакциями и согласованности данных. Он позволяет группе операций рассматриваться как единое целое, обеспечивая откат всех изменений при возникновении ошибки.

```python
class UnitOfWork:
    def begin_transaction(self):
        pass

    def commit(self):
        pass

    def rollback(self):
        pass
```

### 5.5 Presentation Layer (UI)

Основная роль UI — предоставить пользователю удобные интерфейсы для взаимодействия с системой, передавая запросы на обработку нижним слоям.

#### 5.5.1 Маршрутизация и контроллеры

- **Controllers**: принимают запросы от пользователей и передают их в слои бизнес-логики. Например, контроллер заказов отвечает за передачу данных сервиса заказа.

```python
@router.post('/orders/create')
def create_order(request_data: dict):
    try:
        service = OrderService()
        new_order = service.create_order(request_data)
        return {'message': 'Заказ успешно создан.', 'order_id': new_order.id}
    except Exception as ex:
        return {'error': str(ex)}
```

#### 5.5.2 Представление данных

Данные возвращаются пользователю в виде структурированных объектов (JSON, XML), либо посредством передачи данных на фронтенд (REST API, GraphQL).


### 5.7 Паттерны обработки данных

#### 5.7.1 Strategy pattern

Применяется для управления разными способами расчета стоимости или валидации данных.

```python
class CostCalculatorStrategy(ABC):
    @abstractmethod
    def calculate_cost(self, product):
        pass


class StandardCostCalculator(CostCalculatorStrategy):
    def calculate_cost(self, product):
        return product.weight * product.material.price_per_unit
```

#### 5.7.2 Factory Method

Используется для создания сложных объектов, таких как экземпляры заказов или расчётов.

```python
class OrderFactory:
    @staticmethod
    def create_order(customer, product_list):
        order = Order()
        order.customer = customer
        order.products.extend(product_list)
        return order
```

### 5.8 Workflow обработки данных

Рассмотрим пример жизненного цикла обработки заказа:

1. **Создание заказа**: контроллер принимает запрос от пользователя и вызывает сервис создания заказа.
2. **Проверка условий**: сервис проводит валидацию введённых данных и проверяет наличие материалов и свободного принтера.
3. **Подготовка к печати**: система производит необходимое количество моделей и размещает их на виртуальном печатном столе.
4. **Выполнение печати**: выполняется печать, и система обновляет состояние заказа.
5. **Закрытие заказа**: после успешного завершения печати производится оплата и закрывается заказ.

### 5.9 Архитектурный шаблон

Общая структура соответствует стандартному подходу MVC (Model-View-Controller), адаптированного под современные тенденции проектирования приложений.

- **Model**: представляемые сущности (заказы, товары, материалы).
- **View**: интерфейс пользователя (Nuxt/Vue).
- **Controller**: точки входа для обработки запросов и взаимодействия с бизнеслогикой.

### 5.10 Устойчивость и масштабируемость

Для обеспечения устойчивости и масштабируемости:

- Используется кэширование (Redis) для ускорения чтения часто запрашиваемых данных.
- Применяются фоновые задачи (Celery) для длительной обработки (например, пересчета стоимости большого заказа).
- Введены триггеры для предотвращения потери данных (Unit of Work).

### 5.11 Безопасность данных

Для защиты данных применяются стандартные практики:

- SSL-шифрование соединений.
- Авторизация и аутентификация пользователей.
- Валидация данных перед сохранением.

### 5.12 Методы восстановления данных

Имеются встроенные механизмы для резервного копирования и восстановления данных. Используя автоматические процедуры, обеспечивается ежедневное архивирование базы данных.

## 7. Методы и примеры использования

Приведём примеры методов и запросов, используемых в системе.

### 7.1 Методы бизнес-логики

#### Пример метода для определения общего веса одного заказа

```python
class OrderService:
    # Поля определены выше
    def calculate_total_weight(self):
        """
        Рассчитать общий вес всех изделий заказа
        """
        total_weight = sum(product.weight for product in self.products.all())
        return total_weight
```

### 7.2 SQL-запросы

#### Пример 1: Поиск незавершённых заказов конкретного пользователя

```sql
SELECT *
FROM orders o
WHERE o.customer_id = %d AND o.status != 'Завершен';
```

#### Пример 2: Определение суммы материальных затрат на конкретный продукт

```sql
SELECT SUM(p.weight * m.price_per_unit)
FROM products p
JOIN materials m ON p.material_id = m.id
WHERE p.order_id = %d;
```
